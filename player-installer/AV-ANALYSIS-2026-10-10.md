# ModLab installer antivirus analysis — 2026-10-10

Scope: the alpha.5 standard installer, its C# worker and the eight runtime
files were evaluated separately. This document records what was established
from source, build and current vendor documentation, what was changed for the
alpha.6 candidate, and what remains unresolved. **No false-positive
determination is claimed** and no vendor has disclosed its detection rule.

## 2. Component analysis

### 2.1 Setup EXE

- The observed label alone does not disclose Microsoft's exact detection
  rule. [Microsoft's naming documentation](https://learn.microsoft.com/en-us/defender-xdr/malware-naming)
  describes suffixes after `!` as internal indicators. This report does not
  infer a particular feature or rule from the label.
- The standard Setup is unsigned and contains a compressed runtime package
  and a worker executable extracted to `%TEMP%` and launched during
  `PrepareToInstall`. These are measured packaging properties, not proof of
  the cause of any engine's detection.
- Reviewed installer sources perform verified file transactions and do not
  download code, change execution policy, install a service or edit character
  saves. `Uninstallable=no` disables Inno's generated uninstaller; that setting
  by itself does not establish a general absence of persistence.
- Product metadata and an icon were added for normal publisher identification.
  Their effect on antivirus classification cannot be assumed. No vendor has
  confirmed a false positive or disclosed its rule for these files.

### 2.2 Worker

- McAfee's `Ti!56E2CECBA9FC` suffix matches the first 12 characters of the
  worker's SHA-256. This observation does not establish whether the detection
  comes from a hash lookup, a model or another rule. Microsoft and Zillya
  reported Undetected for this worker at the recorded scan time.
- PE inspection: IL-only x64 .NET Framework 4.8 assembly, no overlay, one
  P/Invoke (`kernel32.dll!GetLongPathName`). Independent compilation matched
  the released worker's 95 method records (94 IL bodies), references,
  constants and P/Invoke declarations.
- Behaviour is a hash-verified file transaction with backups and rollback.
  The process-name check (`AssertClosed`) and Steam registry reads are
  required functionality and read-only respectively.

### 2.3 Runtime files

- The eight runtime files are byte-identical to the approved manual package.
  Rebuilding them was explicitly avoided. The ZIP's 0/61 result does not
  establish that every engine examined every contained file, and is not a
  clearance of the EXE.

## 3. Changes in the alpha.6 candidate (installer-only)

Applied because they are the concrete, documented packaging gaps; none of
them weakens verification, backups, rollback or uninstall:

1. **Custom icon** for the Setup EXE and the worker
   (`player-installer/ModLab.ico`, generated by `tools/make_modlab_icon.py`).
   Previously the Setup carried Inno Setup's shared default icon, the same
   default used by a very large number of Inno-based samples.
2. **Complete version metadata**: `VersionInfoCompany`,
   `VersionInfoDescription`, `VersionInfoProductName`,
   `VersionInfoProductVersion`, `VersionInfoProductTextVersion`,
   `VersionInfoCopyright`, `VersionInfoOriginalFileName` in the Setup, and
   `AssemblyProduct`/`AssemblyCopyright`/`AssemblyConfiguration` in the
   worker.
3. **Optional code-signing step** in `tools/build_standard_installer.ps1`:
   `-SignToolPath` + `-SignCertificateThumbprint` sign the worker before Inno
   embeds it and sign the compiled Setup afterwards, then verify the
   signature. The build is unchanged when no certificate is supplied; the
   build record now carries `Signed`, `WorkerSigned`, `SignerCertificate`,
   `Icon` and `IconSHA256`.

Not changed: runtime bytes, transaction logic, security checks, compression,
wizard flow. No obfuscation, no antivirus exclusion, no hash-only rebuild.

## 4. What each measure can and cannot do

| Measure | Can | Cannot |
| --- | --- | --- |
| CA-issued code signing (standard build supports it) | Verifies publisher identity and file integrity; may build publisher reputation | Guarantee zero antivirus or SmartScreen warnings; no certificate is available here |
| Icon + full metadata | Identifies the product and publisher | Establish or guarantee reclassification |
| Microsoft file submission | Allows Microsoft to review a specific detected file | Clear other vendors' classifications |
| SecureAge/Zillya submissions | Request review of exact alpha.5 hashes; submission acknowledgements were recorded | Guarantee approval or a response date |
| Publisher/file reputation | May improve through normal distribution | Guarantee a warning-free first download |

[Microsoft's SmartScreen guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation)
explicitly says newly created signed files can still produce warnings.

## 6. Remaining blockers before Nexus promotion

1. **Unresolved detections** remain on alpha.6. It is not recommended for
   distribution solely on the basis of functional tests.
2. **Publisher signing** is not available here and would not guarantee AV
   acceptance. Standard build support is retained for a future certificate.
3. **Microsoft WDSI false-positive submission** of the new EXE if Microsoft
   flags it (not yet submitted for any build); resubmit SecureAge/Zillya only
   if the new hash is flagged.
4. **Nexus review** of the quarantined uploads / a new file once the scans
   and submissions are recorded.

The earlier functional guarantee is unchanged: eight verified runtime files,
hash-gated installation, backups, rollback and removal/restore, no save
editing, no PowerShell in the player path. Antivirus acceptance is a separate,
still-unresolved release requirement.
